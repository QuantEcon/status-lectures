# PLAN — status-lectures scaffolding

Implementation plan for [QuantEcon/status-lectures#1](https://github.com/QuantEcon/status-lectures/issues/1),
part of the centralized environment & config reporting initiative
([QuantEcon/meta#321](https://github.com/QuantEcon/meta/issues/321)).

This repo is the **central data store + dashboard**. The data **producer**
(publish-time manifests from `publish-gh-pages`) is tracked separately in
[QuantEcon/actions#30](https://github.com/QuantEcon/actions/issues/30); the two
share a versioned schema.

## Goals

- A GitHub-native JSON store of the *effective* build environment/config per
  lecture series, updated on every publish (`repository_dispatch`) with a daily
  scrape as backstop for not-yet-migrated repos.
- A GitHub Pages dashboard rendering the cross-cutting features/config table.
- Stable raw-JSON URLs that downstream consumers can pull from:
  - `QuantEcon.manual` — features table + per-series env block
    ([QuantEcon/QuantEcon.manual#94](https://github.com/QuantEcon/QuantEcon.manual/issues/94))
  - `action-activity-report` — week-over-week env diffs
    ([QuantEcon/action-activity-report#25](https://github.com/QuantEcon/action-activity-report/issues/25))

## Design decisions

### Repo layout

```
data/
  index.json                  # registry: repos tracked, source (publish|scrape), last-updated
  series/
    lecture-python-intro.json # one file per series — latest snapshot only
    lecture-jax.json
    ...
schema/
  series-record.schema.json   # JSON Schema, versioned via schema_version field
scripts/
  intake.py                   # validate + commit a dispatched manifest
  scrape.py                   # backstop: scrape _config.yml + environment.yml
  build_dashboard.py          # render static HTML from data/
.github/workflows/
  intake.yml                  # repository_dispatch receiver
  backstop.yml                # daily scheduled scrape
  pages.yml                   # build + deploy dashboard on data/ changes
site/                         # dashboard templates/assets
```

**Latest-snapshot-per-file, history via git.** Each series file holds only the
current record; week-over-week diffs come from git history of `data/series/*.json`
(`git log -p`, or compare blobs at two dates). This keeps the store small,
makes diffs free, and matches the "diffs are the pushed signal, full data is
pulled" decision in meta#321.

### Record schema (sketch — final ownership shared with QuantEcon/actions#30)

Follow the conventions of `action-activity-report`'s `report-data.json`
(integer `schema_version`, flat snake_case fields, ISO 8601 timestamps):

```jsonc
{
  "schema_version": 1,
  "repo": "lecture-python-intro",
  "collected_at": "2026-06-11T02:00:00Z",
  "source": "publish",              // "publish" (effective) | "scrape" (declared)
  "build": {
    "runner": "ubuntu-latest",      // or AWS GPU runner label
    "gpu": false,
    "container": null,              // or { "image": "...", "tag": "...", "digest": "..." }
    "cache": { "strategy": "...", "hit": true },
    "duration_seconds": 1234
  },
  "environment": {
    "python": "3.13.2",
    "anaconda_pin": "anaconda=2025.06",
    "jupyter_book": "1.0.4",
    "theme": { "name": "quantecon-book-theme", "version": "0.8.2" },
    "sphinx_extensions": { "sphinx_exercise": "1.0.1", ... }
  },
  "config": {
    "execute_mode": "cache",
    "execute_timeout": 600,
    "only_build_toc_files": true,
    "launch_buttons": ["colab"],
    "intersphinx": ["..."]
  },
  "drift": null                     // backstop-detected declared-vs-effective drift, or details
}
```

### Tracked repos

Source lecture repos only — exclude `.notebooks` output mirrors. Initial
registry (from the org repo list): `lecture-python-intro`,
`lecture-python-programming` (+ `.fa`, `.zh-cn`), `lecture-python.myst`
(+ `.zh-cn`), `lecture-python-advanced.myst`, `lecture-jax`, `lecture-dp`,
`lecture-datascience.myst`, `lecture-julia.myst`, `lecture-intro.zh-cn`,
`lecture-stats`, `lecture-wasm`. Registry lives in `data/index.json` so adding
a series is a one-line data change.

### Dashboard

Static HTML generated by a small Python script (no Jekyll, no webapp —
consistent with the no-hosting ops decision). A `pages.yml` workflow rebuilds
and deploys via `actions/deploy-pages` whenever `data/` changes. v1 is one
page: the cross-cutting table (rows = series, columns = the tracked fields)
with publish-push vs scrape badges — which doubles as the **migration tracker**
noted in actions#30.

### Development workspace

This repo is the **primary working repo** for the initiative. The sibling
repos are cloned into a gitignored `repos/` folder so the schema contract and
producer/consumer code can be developed side-by-side:

```
repos/
  actions/                  # producer (QuantEcon/actions#30)
  QuantEcon.manual/         # manual views (#94) + naming convention (#95)
  action-activity-report/   # weekly diffs (#25)
  meta/                     # umbrella issue lives here
```

Each clone keeps its own git remote; changes to those repos are committed and
PR'd from within `repos/<name>/` as usual.

## Phases

### Phase 1 — Schema + store layout
- [ ] Write `schema/series-record.schema.json` (v1) and a `docs/` page describing it; review against the producer field list in actions#30.
- [ ] Create `data/index.json` with the initial registry above.
- [ ] `scripts/intake.py`: validate a manifest against the schema, write `data/series/<repo>.json`, update `index.json`.

### Phase 2 — Dispatch intake
- [ ] `intake.yml`: trigger on `repository_dispatch` (event type `env-manifest`), run `intake.py` on `client_payload`, commit.
- [ ] Concurrency group on the workflow (serialize commits; multiple lectures can publish simultaneously).
- [ ] Document the sender contract for actions#30: event type, payload shape, and the org token/App needed to dispatch into this repo.

### Phase 3 — Daily backstop
- [ ] `scripts/scrape.py`: for registry repos without a recent publish-push record, fetch `_config.yml` + `environment.yml` via the GitHub API and synthesize a `source: "scrape"` record (declared env).
- [ ] Drift check: where both declared and effective data exist, populate `drift` when they disagree.
- [ ] `backstop.yml`: daily cron + `workflow_dispatch` for manual runs.

### Phase 4 — Dashboard
- [ ] `scripts/build_dashboard.py` + minimal template/CSS → `_site/index.html`.
- [ ] `pages.yml`: build + deploy on push to `main` touching `data/` or `site/`.
- [ ] Enable Pages (deploy-from-Actions) on the repo.

### Phase 5 — Seed end-to-end (depends on actions#30 producer)
- [ ] Pick one series (suggest `lecture-python-intro` — actively maintained, standard conda build) and wire publish → dispatch → store → dashboard.
- [ ] Verify the backstop correctly skips it once publish-push records flow.
- [ ] Hand off consumer URLs: raw `data/series/<repo>.json` + `data/index.json` to QuantEcon.manual#94 and action-activity-report#25.

## Risks / open questions

- **Payload size:** `repository_dispatch` `client_payload` is capped (~64 KB).
  A full `conda list` won't fit reliably — the producer should send the curated
  field set above, not the full resolved env. If we later want full lockfiles,
  store them as a build artifact and have intake fetch by URL. Needs agreement
  in actions#30.
- **Dispatch auth:** cross-repo `repository_dispatch` needs a token with write
  access to this repo (org App or fine-grained PAT as an org secret available
  to the lecture repos). Decide which existing org credential to reuse.
- **Schema ownership:** the schema is defined here (`schema/`) but the producer
  emits it — changes require a `schema_version` bump and a coordinated note on
  actions#30. Intake should reject records with an unknown major version
  rather than committing them silently.
- **Translations:** `.zh-cn` / `.fa` repos usually mirror the parent's config —
  track them as first-class rows anyway; the table will make any divergence
  visible, which is the point.
